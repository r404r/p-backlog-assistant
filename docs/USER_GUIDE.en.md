## 1. Getting started

### What this app does

The app caches Backlog issues and user information in a **local SQLite database** and lets you search, filter, and export that cache to Excel. The only screen that writes to Backlog is "Bulk Update & Add"; searching and exporting never change anything in Backlog.

There are three main use cases.

| What you want to do | Screen to use |
|---|---|
| Filter issues by conditions and export them to Excel | Issues |
| Apply edits made in Excel to many issues at once, or add many issues at once | Bulk Update & Add |
| Export users, teams, and project membership to Excel | User Export |

### Requirements

- Windows 10 / 11 (x64) or macOS (Universal)
- A Backlog API key (retrieving the complete user list requires administrator or project administrator permission)
- Only HTTPS connections to `*.backlog.jp` / `*.backlog.com` can be used

### Installation

1. Download the zip for your OS from [Releases](https://github.com/r404r/p-backlog-assistant/releases).
2. Unzip it.
3. Run `backlog-assistant.exe` (Windows) or `Backlog Assistant.app` (macOS).

**Note: the distributed binaries are not code-signed on either Windows or macOS at this time.** Please use only builds downloaded from the official Releases page above.

- **Windows**: SmartScreen may warn you on the first launch. Choose "More info" -> "Run anyway".
- **macOS**: because the app is neither signed nor notarized, Gatekeeper blocks the first launch. After you try to open it once, go to "System Settings -> Privacy & Security" and choose "Open Anyway" near the bottom.

### A note on language

The interface is available in Japanese and English, and you can switch it on the About screen (see [3.5 About](#35-about)). Note that **some messages generated by the backend, and the Excel exports and bulk update templates, are currently in Japanese only**; messages quoted in this guide are given in English even where the app still shows them in Japanese.

### Layout

The sidebar on the left switches between six screens. The `≡` button at the top left collapses the sidebar, and the collapsed state is remembered on the next launch. The current version is shown at the bottom of the sidebar (hidden while collapsed).

Drag the right edge of the sidebar to adjust its width between 140 and 360 px. Dragging it below 120 px collapses it, and dragging right while collapsed expands it again. Double-click the right edge to restore the default width (200 px). The adjusted width is also remembered on the next launch.

| Menu | Contents |
|---|---|
| Connection | Add, edit, delete, and switch connection profiles |
| Issues | Sync, search, and export issues to Excel |
| Bulk Update | Export a template, import it, and write changes in bulk |
| Users | Sync, filter, and export users to Excel |
| Sync Status | Last sync time per data type, manual sync, rate limit remaining |
| About | Version, where data is stored, operation log, appearance (dark mode) switch, language switch |

## 2. Initial setup (Connection Settings)

### 2.1 Getting a Backlog API key

1. Log in to Backlog in your browser.
2. Open "Personal Settings" from the user icon at the top right.
3. Open "API" in the left menu.
4. Enter a memo (a name that describes what the key is for) and register it; an API key is issued.
5. Copy the issued API key.

Backlog may let you display the key again later, but **an API key saved in this app cannot be displayed again**. Please handle it with care.

### 2.2 Creating a profile

On the first launch, the Connection Settings screen shows a "Welcome" message.

1. Click "Register a profile" (from the second profile onward, use the "Add new" button below the profile list).
2. Enter a **Profile name** that is easy to recognize (for example, "For the dev team").
3. Enter the **space URL** in the form `https://example.backlog.jp`.
   - Only `*.backlog.jp` / `*.backlog.com` URLs starting with `https://` can be used.
   - URLs containing a port number, path, or query string cannot be registered.
4. Paste the **API key** you copied in 2.1.
5. Click "Test connection".
6. When "Connection test succeeded" appears together with "User name:" and "Permission status (provisional):", click "Save".

> **Tip**: the "Save" button stays disabled until the connection test succeeds. Editing the space URL or the API key invalidates the test result, and you have to test again.

After saving, the app calls the API and shows the confirmed permission status.

### 2.3 Where the API key is stored (secure design)

- API keys are stored **only in the OS keychain** (Windows Credential Manager / macOS Keychain). They are never written to the `config.json` configuration file or to the local DB.
- Once saved, an API key cannot be displayed again in the app.
- When editing a profile, leaving the API key field empty keeps the current key.
- API keys are not written to the operation log either (only a boolean recording whether a key was entered).

### 2.4 Feature availability by permission

Which features you can use depends on your permission in Backlog. The status shown during the connection test is a **provisional judgment** based on your role (roleType); the confirmed status is shown after saving. (The permission status on the Connection Settings screen is shown only immediately after saving. To check it later, look at the top of the User Export screen.)

| Permission status message | Effect |
|---|---|
| Administrator features are available (both the user list and the team list can be retrieved) | User Export can retrieve all users and teams in the space |
| Some administrator features are unavailable (no permission for the user list; user retrieval falls back to per-project. The team list can be retrieved) | User Export falls back to the scope of your member projects |
| Some administrator features are unavailable (no permission for the team list; the user list can be retrieved) | Only the teams that could be retrieved via your member projects are reflected (if anything may be missing, deletions are not applied) |
| Administrator features are unavailable (no permission for either the user list or the team list; retrieval falls back to per-project) | User Export is assembled from the members of your member projects |

Issues and Bulk Update & Add work with normal user permission, within the scope of your member projects.

### 2.5 Switching and deleting profiles

- You can register multiple spaces. Switching with the "Connection:" selector at the top of the Connection Settings screen is remembered on the next launch.
- Delete a profile with the "Delete" button in the list. If you leave **"Also delete the local data (DB) (recommended)"** checked in the confirmation dialog, both the API key in the OS keychain and the local DB are deleted. If you uncheck it, the data already fetched (which may include personal information) remains on your computer.
- There is one local DB file per "space host x connected user". Therefore, **if another profile that connects to the same space as the same user still exists, the DB is shared and is not deleted** (to avoid deleting data that is still in use). A profile whose connection test has never succeeded has no DB, so there is nothing to delete.

## 3. Screen-by-screen guide

### 3.1 Issues

#### What you can do

Sync issues from Backlog into the local DB, search and filter that local data, and export the results to Excel.

#### Basic steps

1. Choose the target project in the **Project** selector. If the list is out of date, click "Sync project list" (this button only updates the list of projects; it does not sync issues).
2. Choose a sync mode in the **Sync** section and click "Sync".
   - **Auto (full sync on the first run)**: decided from the sync state (a full sync is used if the project has never been synced or has not been synced for a long time). This is normally all you need.
   - **Full sync**: re-fetches all issues in the project.
   - **Incremental sync**: fetches only the updates since the last sync.
   - While syncing, progress is shown as, for example, "Fetching 1,200 / 5,000". When it finishes, the app reports the numbers fetched, added/updated, and deleted, along with the elapsed time.
3. Specify the **search conditions**.
   - **Keyword**: a partial match against the **issue key, summary, and description** stored in the local DB (paste an issue key to narrow the list quickly. Because it is a partial match, `EXA-1` also matches `EXA-10`, for example). Separating words with spaces (half-width or full-width) makes them multiple keywords, and you can choose "Match all (AND)" or "Match any (OR)". Pressing **Enter** in the field also runs the search.
   - **Updated / Created**: filter by a date range.
   - **Status / Assignee**: choose from candidates built from the issues already synced.
   - **Filter by custom fields**: shown only for projects that have custom field definitions. The input method depends on the type (text and text area are partial matches; number and date are ranges; single/multiple list, checkbox, and radio are selected from their options).
4. Click "Search".
5. If needed, choose the columns in the **Excel export** section, click "Export to Excel", and choose where to save the file.

#### Tips and notes

- Search results are shown **200 rows per page**. The count reads "Matches: N (showing x–y)", and the pager below the result table ("« First", "‹ Previous", "Next ›", "Last »", and a **"Page number (press Enter to move)" field**) lets you browse everything. Press Enter in the field to jump. Out-of-range values are corrected into the valid range (values below 1 go to the first page; values beyond the last page go to the last page). If everything fits on one page, the pager is hidden. Excel always receives **all** matching rows, regardless of the page shown.
- If an **issue sync finishes** while you are paging, or you use **"Get the latest state"** in the detail popup, the results on screen may no longer match the DB, so the app shows "The data has been updated. Search again to see the latest results." and disables paging until you search again. Clicking "Search" once more clears it.
- **Clicking an issue key in the result list opens the details of that issue in a popup** (status, issue type, priority, assignee, due date, created/updated date and time, parent issue, custom fields, and the description body). The contents are **as of the time the issue was imported locally** (normally the last sync); no request is sent to Backlog when the popup opens. The note at the bottom of the popup shows that timestamp. Close the popup with "Close", the **Esc** key, or by clicking the background. Note that **details cannot be opened while issues are syncing** (an open popup closes automatically when a sync starts).
- Clicking **"Get the latest state"** in the popup re-fetches **only that one issue** from Backlog, applies it locally, and updates both the display and the timestamp in the note (the whole project is not synced, so the "Last synced" value shown in the list does not change). From your next search onward, the new values also appear in the list.
- If the issue has been deleted in Backlog, you get an error saying it may have been deleted, and **the local contents are left as they are** (deletions are applied by a full sync).
- **Comments are not fetched by a sync.** They are fetched and displayed only for issues where you clicked "Get the latest state" (the retrieval state is shown at the top of the popup). For issues where you have not clicked it, the popup shows "Comments have not been fetched. You can fetch them with "Get the latest state"."
- Comments are listed **newest first**, and the comment area scrolls when there are many. Change history entries **with no body text** (status changes and the like) are only counted ("N more change history entries (check them in Backlog)").
- A single retrieval stores **up to the most recent 500 comments**. For issues beyond that, the popup shows "This issue has many comments, so only the latest ones were fetched. Check the older comments in Backlog." Note that comments are covered by neither keyword search nor Excel export.
- **Clicking the clipboard icon to the right of the issue key copies that issue's URL to the clipboard** (a toast reading "Copied the issue URL (ABC-123)" appears at the bottom center for a few seconds). "Copy URL" and "Open in browser" inside the popup do the same thing.
- The columns you can export are Key, Summary, Status, Assignee, Issue Type, Priority, Created, Updated, Due Date, and Parent Issue Key, plus custom fields. Parent Issue Key and custom fields are not selected by default.
- **Selecting a custom field in the column selection also adds that column to the search results** (search again after selecting it to apply the change).
- The exported workbook consists of a `課題` (Issues) sheet and an `情報` (Info) sheet that records the row count.
- If more than **1,000,000** rows match, the export fails with an error saying the target count exceeds the limit of 1,000,000 and asking you to narrow the conditions, and no file is created.
- Searching and exporting always work against the local DB. **Sync first to see the latest state from Backlog.**
- Keyword search covers only the issue key, summary, and description stored locally; comments and attachments are out of scope. This differs from the keyword search on the Backlog site. Also, because the issue key is matched partially, entering just a project key matches every issue in that project.
- While a sync is running you cannot switch projects, search, export to Excel, or open issue details (so that partially imported data is never read).

### 3.2 Bulk Update & Add

#### What you can do

Export the issues of the target project to an Excel template, edit them in Excel, and apply the changes to Backlog in bulk. Rows with an empty `issueKey` are added as new issues.

> **This feature changes data in Backlog.** The first time you use it, we recommend trying it on a test project where you are the only member.

#### Basic steps

1. **① Export template**: choose a project, optionally specify the "Conditions for the issues to export" (keyword, updated, created, status, assignee), then click "Export template" and choose where to save the file.
   - **Only the issues matching the conditions** are included in the template. **If every field is blank, all issues in the target project** are exported.
   - The conditions are the same as the search conditions on the Issues screen and are applied to the synced local data (filtering by custom field is not supported here). The status and assignee choices are built from the issues already synced, so they are empty for a project that has never been synced.
   - Pressing Enter in the keyword field does not export. Always use the "Export template" button.
   - **Important**: the template export can write up to 1,000,000 rows, but **the import limit is 50,000 rows**. If the export produces more than 50,000 rows, it cannot be imported as is. **Narrow the conditions, delete unnecessary rows in Excel, or split the file before importing** (you may delete whole rows freely; blank rows count toward the row limit even though they are treated as "no change").
2. Open the exported workbook and edit the `一括更新` (Bulk update) sheet. See [4. Rules for filling in the Excel template](#4-rules-for-filling-in-the-excel-template) and the `記入方法` (How to fill in) sheet in the template.
3. **② Import Excel**: optionally choose a "Default priority" (applied to new rows that have no priority), click "Import Excel", and select your filled-in file. **This operation does not write to Backlog.**
4. Review **③ Validation result and change preview (dry run)**.
   - The top shows "Imported N rows / Add new N / Update N / No change N".
   - If there are validation errors, the app shows "N validation errors (fix them and import again)" with row numbers, and the run is blocked.
   - The "Changes" column in the list shows the before and after values per row.
   - Rows whose "Conflict" column says "Check" have been updated remotely since the template was exported.
5. **④ Run**: clicking "Run" shows a confirmation. Review "N rows will be written to Backlog. Are you sure?" and click "Write".
   - Progress is shown during the run as a progress bar and "N / M (x%)".
   - Clicking "Cancel" requests a stop. Processing stops after the row being sent finishes.
6. **⑤ Result**: the numbers succeeded, failed, conflicting, and skipped are shown along with the elapsed time. "Export result to Excel" writes the per-row result (done, failed, conflict, error details).
   - Rows where a new issue was added record **the key of the created issue** (the `issueKey` column) and the issue ID (the `作成された課題ID` (created issue ID) column of the result workbook). "Show details" in the job history also shows them as, for example, "(New) PROJ-123". Use this to find the issues you added later on.
7. **⑥ Job history**: past imports and runs are listed. If a run was interrupted, resume it from here.

#### Tips and notes

- **Issues are written to Backlog one at a time** (there is no bulk API). API calls are spaced by at least one second. A create uses one call, while an update uses two including its conflict check, so 1,000 rows take at least about 17 minutes when all are creates or about 34 minutes when all are updates. Network latency and rate-limit waits add more time. The screen shows a minimum estimate based on the create/update mix.
- **Conflict detection**: immediately before writing, the app checks the remote updated timestamp, and if it has changed since the template was exported (`base_updated`), **the row is excluded as a conflict instead of being written**. Use "Overwrite conflicts and run again" only when you do want to overwrite (changes made remotely will be lost).
- **Duplicate-creation protection**: rows whose send result is unknown (5xx, missing response, etc.) are held in the sending state (the row details and the result workbook show "Sending (result unconfirmed)"). The job history shows a notice starting with "The send result of some rows could not be confirmed (N rows).", and "Resume and resend the sending rows" matches them against the already created issues before re-sending them safely.
- Each row in the job history offers "Resume", "Overwrite conflicts and run again", "Show details", and "Export result to Excel". Jobs that still have rows counted as "Pending" or "Sending" can be resumed.
- "Skipped" in the result counts the rows judged as "no change" at import. Rows left unprocessed by a cancellation or an interruption are not included; check "Pending" and "Sending" in the job history for those.
- The history and row details of completed jobs are kept for **90 days** and then deleted automatically.
- While issues are syncing you cannot switch projects, export a template, import an Excel file, or run a bulk update (reviewing the job history and exporting results to Excel are still available).

### 3.3 User Export

#### What you can do

Extract the user list along with teams, roles, member projects, and administered projects, and export it to Excel.

#### Basic steps

1. Check the **Permission status** at the top of the screen (if it has fallen back, the retrievable scope is limited).
2. **Sync the project list first.** Run "Sync project list" on the Sync Status screen (or on the Issues screen).
   - User sync builds the member projects, the administered projects, and (when permission has fallen back) the set of users itself **from the local project list**.
   - **This step is required even if you have administrator permission.** Syncing users while projects are unsynced does **not** raise an error; it simply produces empty "Projects" and "Admin Projects" columns.
3. Click "Sync users" in the **Sync** section. This fetches the user list, teams, and project membership/administrator information and updates the local DB.
4. Specify the **Search conditions**.
   - **Keyword**: partial match on name, user ID, or email address.
   - **Role**: All / Administrator / Normal User / Reporter / Viewer / Guest Reporter / Guest Viewer.
5. Click "Search".
6. Choose the columns under **Excel export** and click "Export to Excel".

#### Tips and notes

- The screen shows the first **200** rows only. All matching rows are written to Excel.
- The exportable columns are User ID, Name, Email Address, Role, Role Value, Teams, Projects, and Admin Projects. "Role Value" (the numeric roleType) is not selected by default.
- "Role" is the space-wide permission. For per-project permissions, see the "Projects" and "Admin Projects" columns.
- **User list fallback**: without administrator permission the app cannot fetch the space-wide user list, so it assembles user information from the members of your member projects. In that case, if projects have not been synced, the sync stops with an error explaining that the space-wide user list cannot be fetched, that user information must be assembled from project members, and that projects must be synced first.
- **Team list fallback**: when the space-wide team list cannot be fetched, the app supplements it with the team list of each member project. **The outcome differs between "no permission" and "a temporary communication error"** (both appear under the warnings of the sync result).

  **A. No permission for the team list (403)** — the app can conclude that permission has been reduced, so it also applies deletions.

  | Situation | Result |
  |---|---|
  | Projects have not been synced | The target set cannot be determined, so existing team information is **left as is** |
  | Team retrieval failed for some projects | Only what could be fetched is applied, and **deletions are not applied** |
  | All projects were fetched successfully | Team information is **replaced** with what was fetched (deletions included) |
  | All projects were fetched but returned no teams at all | The team information **cache is discarded** so that stale data is not kept |

  **B. Temporary communication errors and other non-permission reasons** — to avoid losing information because of a transient failure, **neither replacement nor cache discarding is performed**.

  | Situation | Result |
  |---|---|
  | At least one team was fetched via a project | Only what could be fetched is applied, and **deletions are not applied** |
  | Nothing could be fetched | Existing team information is **left as is** |

- User information assembled during a fallback may have empty values for items that per-project responses do not include, such as email addresses.

### 3.4 Sync Status

#### What you can do

Check how fresh each data type is (its last sync time) and run syncs manually. You can also check the rate limit remaining.

#### Basic steps

1. Check freshness in the **Last sync time per data type** table ("Last synced" and "Elapsed"). A completion time is recorded for these three types.
   - **Projects** (entire space): updated by "Sync project list".
   - **Issues** (one row per project): updated by "Sync issues".
   - **Users** (entire space): updated by "Sync users" on the User Export screen. Teams and project members are included in the user sync but are not listed as separate rows.
2. Under **Manual sync**, choose a project and a sync mode (auto / full sync / incremental sync) and click "Sync issues".
3. To update only the project list, click "Sync project list".

#### Tips and notes

- **Rate limit remaining** shows "Remaining / limit (per minute)" and the reset time for each category (Read / Update / Search / Icon). The display **refreshes automatically every 10 seconds**, but the values are observed from server responses, so **refreshing the display never consumes the API**. For a category you have not used yet, it shows "Not observed yet (shown after the API is used)".
- Issue sync uses the "Search" quota; bulk update writes use the "Update" quota.
- The location of the operation log is shown at the bottom of the screen as "Log file:".
- If an issue sync started on another screen is running, the reason is shown together with the target project name, and switching projects and syncing are unavailable.

### 3.5 About

#### What you can do

Check the version, contact, and license, see where data is stored on this computer, switch the **appearance (dark mode)**, and switch the **display language**.

#### What is shown

- **Version / Author / GitHub / Documentation / Contact / License**: please report bugs and requests to GitHub Issues. The "README" and "User Guide" links under "Documentation" open in your default browser.
- **Appearance**: choose from "Match system (default) / Light / Dark". The choice is applied immediately and persists across restarts. "Match system" follows the appearance (dark mode) setting of your OS, so changing the OS setting changes the app as well.
  - The window frame (title bar) **follows the selected theme on Windows**. **On macOS it follows the OS appearance setting**, so if you explicitly select light or dark inside the app, the title bar may keep the OS colors (a macOS limitation).
- **言語 / Language**: choose from "Match system (default) / 日本語 / English". The choice is applied immediately across the whole interface and persists across restarts. "Match system" follows the language setting of your OS and browser (the app runtime), and non-Japanese environments are displayed in English. The "README" and "User Guide" links under "Documentation" also open the Japanese or the English version according to the selected language.
  - **Current limitation**: some messages generated by the Go backend (validation errors and the detailed text of processing results), as well as the headers and the `記入方法` (How to fill in) sheet of the Excel exports and bulk update templates, are currently available in Japanese only. You can keep using the app in English, but those parts are displayed and exported in Japanese.
- **Storage location mode**: how the location of the configuration and the local DB is determined ("Default (user config folder)", "Environment variable (BACKLOG_ASSISTANT_HOME)", or "Portable (portable.txt)"). See "[5.4 Changing the storage location](#54-changing-the-storage-location)" for how to change it.
- **Config folder**: where the connection profiles (`config.json`) are stored.
- **Local DB**: the file path and size per profile (the total including the WAL and SHM files). If it has not been created yet, it shows "Not created yet (created after a connection test)". **You can delete the local DB; the app can fetch the data again.**
- **Operation log**: the output path. Attaching it to a bug report speeds up the investigation.

The API key is not stored in any of the files above; it is stored only in the OS keychain.

## 4. Rules for filling in the Excel template

This chapter describes how to fill in the Excel template used by "Bulk Update & Add".

The **`記入方法` (How to fill in) sheet** of the template states the main rules (the items where `#CLEAR#` can be used - assignee, due date, description, parent issue key, and custom fields - are noted next to each item on the sheet). This chapter consolidates the explanations scattered across that sheet into tables and adds the following points, which the sheet does not cover.

- The columns where `#CLEAR#` **cannot** be used (summary, issue type, status, priority, `issueKey`, `base_updated`)
- That **`#CLEAR#` cannot be used in any column on a row that adds a new issue**
- That **a status cannot be specified on a row that adds a new issue**
- The limits on file size, number of data rows, and number of columns

> The sheet names and column headers of the template are part of the file format and are currently in Japanese only. They are shown below exactly as they appear in the file, with an English gloss in parentheses.

### 4.1 Sheet structure

| Sheet name | Role |
|---|---|
| `一括更新` (Bulk update) | The data sheet you fill in. Edit this one |
| `記入方法` (How to fill in) | The operating rules, plus a `プロジェクトID` (project ID) row identifying the target project |
| `マスタ` (Master) | The choices for issue type, status, priority, assignee, and single-select custom fields (the source of the dropdowns) |

**Do not edit or delete the `プロジェクトID` (project ID) row** at the top of the `記入方法` sheet. It is checked against the project selected on screen at import time, to prevent writing a template into the wrong project by mistake.

### 4.2 Column layout

The columns of the `一括更新` sheet appear in this order.

`issueKey` / `件名` (Summary) / `種別ID` (Issue Type ID) / `種別名` (Issue Type Name) / `状態ID` (Status ID) / `状態名` (Status Name) / `優先度ID` (Priority ID) / `優先度名` (Priority Name) / `担当者ID` (Assignee ID) / `担当者名` (Assignee Name) / `期限` (Due Date) / `詳細` (Description) / `親課題キー` (Parent Issue Key) / `base_updated` / `属性:{定義名}` (Attribute: definition name — the custom fields, in definition order)

**Do not add, delete, or reorder columns, and do not rename the headers.** Delete unnecessary rows entirely.

### 4.3 Basic rules

| Rule | Details |
|---|---|
| Adding issues | A row with a **blank** `issueKey` is treated as a new issue (a row with a value updates the existing issue) |
| Scope of an update | **Only the cells you fill in** are updated (**blank = leave unchanged**) |
| Clearing a value | To clear a value, enter `#CLEAR#` (leaving the cell blank does not clear it). See the table below for the columns where it works. **This feature is still being verified against a live space** |
| Required values on new rows | The **summary** and the **issue type** (either the type name or the type ID) are required. If the priority is blank, the "Default priority" chosen at import time is applied |
| Restrictions on new rows | `#CLEAR#` cannot be used in any column on a new row (there is no existing value to clear). Also, **a status cannot be specified on a new row** (change the status with a later update) |
| `base_updated` | **Do not edit this column.** It is used for conflict detection (checking whether the remote issue has been updated since the import) |
| Project | The project cannot vary from row to row |
| Whitespace | Leading and trailing whitespace is stripped from every cell at import time |

**Columns where `#CLEAR#` can be used**

| Column | `#CLEAR#` | Notes |
|---|---|---|
| `担当者名` (Assignee Name) / `担当者ID` (Assignee ID) | Supported | Unsets the assignee (`#CLEAR#` in the assignee ID column takes effect only on rows where the assignee name column is blank) |
| `期限` (Due Date) | Supported | Unsets the due date |
| `詳細` (Description) | Supported | Empties the description body |
| `属性:{定義名}` (Attribute: definition name — custom fields) | Supported | Clears the value of that custom field ([4.5](#45-custom-fields)) |
| `親課題キー` (Parent Issue Key) | Supported | Removes the parent-child relationship ([4.6](#46-parent-issue-key)) |
| `件名` (Summary) / `種別` (Issue Type) / `状態` (Status) / `優先度` (Priority) | **Not supported** | These values cannot be emptied |
| `issueKey` / `base_updated` | **Not supported** | These columns identify the issue and drive conflict detection |

> **Note**: entering `#CLEAR#` in the summary, issue type, status, or priority makes the app show an error saying that only the assignee, due date, and description can be cleared. That message covers the fixed-field columns only; **`#CLEAR#` does work in custom field columns and in the parent issue key column** (they are processed separately and are not subject to that error). The message is narrower than the actual behavior, so treat the table above as authoritative.

### 4.4 Name columns and ID columns

Issue type, status, priority, and assignee each have both a "name" column and an "ID" column.

- Edit the **name column**. Selecting a cell in a name column shows a dropdown of the choices from the `マスタ` (Master) sheet.
- **On a row where the name column has a value, the name column always wins.** If the ID column disagrees with it, the ID column is ignored and a warning appears in the import result.
- **On a row where the name column is blank**, the value in the ID column is used.
- Assignee names are exported in the **"Display name (ID)" format** (for example, `Taro Yamada (12345)`) so that people with the same name can be told apart. Choosing from the dropdown produces this format.

### 4.5 Custom fields

- Custom fields are columns named **`属性:定義名`** (Attribute: definition name; they come after the fixed columns).
- As with the other columns, **blank = leave unchanged**, and `#CLEAR#` clears the value (a feature still being verified against a live space).

| Type | How to fill it in |
|---|---|
| Text / text area | Enter the value directly |
| Number | Enter a number |
| Date | Enter it in `yyyy-MM-dd` format |
| Single list / radio | Choose the option name from the dropdown |
| Multiple list / checkbox | Enter the option names **separated by commas** (for example, `UI, DB`). The Japanese comma `、` also works as a separator |

**Notes**

- Values that are not among the options (free text entered as "Other") are **not supported** at this time.
- Multiple list and checkbox fields whose option names contain a comma (or the Japanese comma `、`) cannot be imported, because the separator cannot be distinguished.
- Custom fields **apply to specific issue types**, so writing into a field that does not apply to the row's issue type is an error.
- On a new row, the **required custom fields** that apply to that issue type must be filled in.
- Setting the literal string `#CLEAR#` as a value is not possible via Excel, because it cannot be distinguished from the clear instruction.

### 4.6 Parent issue key

- To set or change the parent issue, enter the **issue key of the parent** (for example, `ABC-1`) in the `親課題キー` (Parent Issue Key) column.
- For an issue that is not available locally (not synced), you can also use the **`ID:<issue ID>`** format (for example, `ID:12345`).
- **Blank = leave unchanged**, and `#CLEAR#` removes the parent-child relationship (removal is still being verified against a live space).

**Restrictions**

- Only issues that already exist in Backlog can be used as a parent (you cannot make two new rows in the same file parent and child).
- Backlog supports **only one level** of parent-child nesting, which means (1) the issue you designate as a parent must not itself be a child issue, and (2) the issue you are giving a parent must not itself have child issues.
- The parent issue must be in the **target project**.
- Issue keys are resolved against the local data, so if one is not found, sync the target project and import again.
- Within the same file, you cannot designate an issue whose parent you removed as the parent of another row (import the removal first, sync, then export the template again).

### 4.7 Example

| issueKey | 件名 | 種別名 | 状態名 | 担当者名 | 期限 | 詳細 | 親課題キー | base_updated | 属性:Severity |
|---|---|---|---|---|---|---|---|---|---|
| ABC-10 | | | Resolved | | | | | 2026-08-01T09:00:00Z | |
| ABC-11 | Fix the wording on the screen | | | Taro Yamada (12345) | 2026-09-30 | | ABC-1 | 2026-08-01T09:05:00Z | High |
| ABC-12 | | | | `#CLEAR#` | `#CLEAR#` | | | 2026-08-01T09:10:00Z | |
| | Add a new issue | Task | | Taro Yamada (12345) | | Organize the steps | | | Normal |

- Row 1: changes only the status to "Resolved" (the other cells are blank, so they are left unchanged).
- Row 2: changes the summary, assignee, due date, parent issue, and a custom field.
- Row 3: clears the assignee and the due date.
- Row 4: `issueKey` is blank, so a new issue is added (summary and issue type are required).

### 4.8 Limits

| Item | Limit |
|---|---|
| File size | **100 MB** |
| Data rows | **50,000 rows** |
| Columns | 14 fixed columns + the number of custom field definitions + 64 |

Exceeding a limit produces an error such as "the Excel file is too large" or "too many data rows (the limit is 50,000)". Split the file and import the parts separately.

The row limit applies to **"rows that contain at least one cell"**, not to "rows that will be imported". Because a template export can produce up to 1,000,000 rows, **a template for a project with more than 50,000 issues cannot be imported as is.** Narrow the conditions when exporting the template, delete unnecessary rows, or split the file. Also, because API calls are made one at a time with at least a one-second interval and updates require a conflict check, we recommend keeping each run to a few thousand rows in practice.

## 5. Data and security

### 5.1 Storage locations

| Data | Location |
|---|---|
| Configuration (profiles; keys not included) | `<user config dir>/backlog-assistant/config.json` (Windows: `%AppData%\backlog-assistant\config.json`) |
| API keys | OS keychain only (Windows Credential Manager / macOS Keychain) |
| Local DB (fetched data, SQLite) | Same location, `data\<space host>_<user ID>.db` (permissions are 0600 on Unix-like systems; on Windows the ACL of the user directory applies) |
| Operation log | `logs\` in the same folder as the executable (falls back to the user config directory automatically if it is not writable) |

The exact paths are shown on the About screen. The location of the configuration and the local DB can be changed (see "[5.4 Changing the storage location](#54-changing-the-storage-location)").

### 5.2 How sync and the local cache work

- **Searching, filtering, and exporting to Excel all work against the local DB.** They are fast because Backlog is not queried, but **what you see is the state as of the last sync**.
- The only thing that writes to Backlog is a run on the "Bulk Update & Add" screen.
- Incremental sync uses `updatedSince` plus activity-based deletion detection to save API calls. Choose a full sync if you are unsure about consistency.
- While a sync is running, switching projects, searching, exporting to Excel, and bulk updating are blocked on every screen so that partially imported data is never read.

### 5.3 Operation log

- Logs are written per day to `logs/` in the same folder as the executable, named `backlog-assistant-YYYYMMDD.log`. If that folder is not writable (under `Program Files`, inside a macOS `.app` bundle, and so on), the app automatically falls back to `backlog-assistant/logs/` in the user config directory. The actual location is shown as "Operation log" on the About screen.
- Plain-text logs are kept for **14 days**. Older logs are gzip-compressed in the background at startup and moved to `logs/archive/`, where **archives are kept for 90 days**.
- **API keys, issue content, and user names are never recorded.** Space names in URLs and home folder names are masked.
- The logs are designed to be shareable for troubleshooting, but **we recommend reviewing their contents before sharing them**.

### 5.4 Changing the storage location

The **base folder** that holds the configuration (`config.json`) and the local DB (`data/`) can be changed in two ways. This is useful for carrying the app on a USB drive or placing the data on another drive.

| Method | Setup | Base folder |
|---|---|---|
| Portable | Put a `portable.txt` file next to the executable (its contents may be empty) | `userdata\` in the same folder as `portable.txt` |
| Environment variable | Set `BACKLOG_ASSISTANT_HOME` to a folder | The folder you specified |

**Portable use on macOS**: put `portable.txt` **next to the `Backlog Assistant.app` bundle, not inside it** (for example in your Applications folder or at the root of a USB drive, alongside the `.app`). The data is created in `userdata/` at that same level. If you put it inside the bundle, updating the app deletes your data along with it.

**The priority is portable > environment variable > default** (if both are set, the portable location wins). The location is determined once at startup, so restart the app to apply a change. You can see which method is in effect under "Stored Data" → "Storage location mode" on the About screen (one of "Default (user config folder)", "Environment variable (BACKLOG_ASSISTANT_HOME)", or "Portable (portable.txt)").

#### Things to note

- **Switching the location does not move your data automatically.** If the new base folder has no `config.json`, the app starts in its initial state (no profiles registered). **Switching back to the previous location shows your original data again.**
- To keep using your data, **quit the app first, then copy the entire contents of the base folder (`config.json` and `data/`) to the new location.** Copying while the app is running can corrupt the local DB.
- **API keys do not move.** They are stored in the OS keychain, so you have to enter them again on another computer or under another user account (no re-entry is needed on the same computer and user account).
- The operation log location does not change (`logs/` in the same folder as the executable, falling back to the user config directory automatically if it is not writable).
- The environment variable accepts **absolute paths only**. `~` and `%AppData%` are not expanded, and paths containing `?` cannot be used.
- **We do not recommend using a cloud-synced folder (OneDrive, Dropbox, Google Drive, and so on).** The sync process can conflict with local DB (SQLite) writes and corrupt your data.
- If the location you specified cannot be used (the USB drive is disconnected, you have no write permission, the app is installed under `Program Files`, and so on), the app **does not silently fall back to the default location; it stops with a startup error** instead. Falling back would create empty data somewhere else and make it look as if your data had disappeared. The reason is recorded in the operation log, or in `crash.txt` next to the executable (or in the user config directory if that is not writable; neither destination is affected by this setting).

### 5.5 Moving to another computer

Follow these steps to carry your saved profiles and fetched data (the local DB) over to another computer.

1. **Quit the app on the source computer.** While it is running the local DB is being written to, so copied files may be corrupted.
2. **Copy the whole base folder.** With the default location on Windows this is the `%AppData%\backlog-assistant` folder (usually `C:\Users\<user name>\AppData\Roaming\backlog-assistant`); typing `%AppData%` in the Explorer address bar opens it. The exact location is shown as "Config folder" on the About screen.
   - Include **both** `config.json` and `data/`. If `.db-wal` or `.db-shm` files remain in `data/`, copy them as well (leaving them behind can lose your most recent changes).
3. **Paste them into the same location on the target computer.** Make sure the app is closed there too. For portable use, copy the whole set including `portable.txt` and the `userdata` folder.
4. **Start the app on the target computer and enter your API key again.** API keys live in the OS keychain and are not moved by copying folders. Select the profile on the Connection Settings screen, enter the API key, and run a connection test.

## 6. Troubleshooting / FAQ

### The connection test fails

The messages below are produced by the backend and are currently shown in Japanese; an English translation follows each one.

| Symptom / message | What to do |
|---|---|
| 「認証に失敗しました(API キーが無効です)」 (Authentication failed: the API key is invalid) | Check that the API key is correct. Also check that no whitespace or line break was copied with it and that the key has not been deleted or disabled in Backlog (the app also strips leading and trailing whitespace automatically) |
| 「スペース URL は https:// で始まる必要があります」 (The space URL must start with https://) | Enter `https://`, not `http://` |
| 「許可されていないホストです(*.backlog.jp / *.backlog.com のみ利用できます)」 (Host not allowed: only *.backlog.jp / *.backlog.com can be used) | Check the domain of the space URL |
| 「スペース URL にパスを含めることはできません」 (The space URL must not contain a path) | Enter only up to the host name, as in `https://example.backlog.jp` (`/dashboard` and the like are unnecessary) |
| 「権限がありません」 (You do not have permission) | Retrieving the complete user list requires administrator or project administrator permission. See [2.4 Feature availability by permission](#24-feature-availability-by-permission) |

### The app says to sync projects first

If you sync users without administrator permission, the app assembles user information from the members of your member projects, so it cannot proceed while projects are unsynced. Run "Sync project list" on the Sync Status screen (or the Issues screen), then click "Sync users" again.

Note that **with administrator permission this error does not appear, but the "Projects" and "Admin Projects" columns will be empty if projects are unsynced.** Regardless of permission, sync the project list before syncing users.

### A warning says that applying deletions was held back

When there are **100 or more** deletion candidates, the app holds back applying deletions as a safeguard against accidental data loss. **Repeating a full sync does not release this hold automatically.** If you really did delete a large number of issues in Backlog, resolve it as follows.

1. Quit the app.
2. Delete the local DB file (the path is shown on the About screen; delete the matching `-wal` and `-shm` files too).
3. Restart the app and run a full sync.

### A bulk update fails with a "cannot determine" error

This appears when the current value of a parent issue or a custom field cannot be determined from the local data (for example, data synced by an older version). As the message says, **run a full sync of the target project and try again**. The same fix applies when an issue search reports that some issues could not be checked against the custom field conditions because the local issue data is out of date.

### Other operations are unavailable during a sync

Reading the local DB mid-sync would return incomplete results covering "only what has been imported so far". To prevent that, switching projects, searching, exporting to Excel, exporting a template, importing, and running a bulk update are all blocked while syncing. Reviewing the job history and exporting results to Excel remain available. Please wait for the sync to finish.

### SmartScreen warns on Windows / the app will not start on macOS

The distributed binaries are not code-signed.

- Windows: choose "More info" -> "Run anyway".
- macOS: after you try to open it once, go to "System Settings -> Privacy & Security" and choose "Open Anyway" near the bottom.

Please use only builds downloaded from the official [Releases](https://github.com/r404r/p-backlog-assistant/releases) page.

### The app does not start

If startup fails, the cause is written to the operation log. If even the log cannot be opened, the app appends to **`crash.txt`** in the same folder as the executable (or in the user config directory if that is not writable) as a last resort. Please attach this file to your bug report. If an error occurs while a screen is displayed, the app shows "An error occurred while displaying this screen"; switch to another screen or restart the app.

If the record says that the storage location could not be determined, the location you set in [5.4 Changing the storage location](#54-changing-the-storage-location) is unusable (the USB drive is disconnected, you have no write permission, the path is not absolute, the path contains `?`, and so on). Restore the location, or delete `portable.txt` / unset the `BACKLOG_ASSISTANT_HOME` environment variable to start with the default location.

### I keep hitting the rate limit

The Backlog API is rate limited. The app manages the limit per category automatically and waits when it is about to be exceeded (during a bulk run, all API calls are throttled to at least one second apart: writes, conflict checks, and the pre-resend match). Check the remaining amount and the reset time per category under "Rate limit remaining" on the Sync Status screen. If the remaining amount is low, wait until the reset time before running again.

### There is no copy icon next to the issue key

If the space URL cannot be resolved, the app cannot build an issue URL, so the clipboard icon (and "Copy URL" / "Open in browser" inside the popup) is hidden. Check that a profile is correctly selected on the Connection Settings screen (clicking the issue key to see the details still works in this case).

### Searching is slow

- Keywords of one or two characters cannot use the full-text index and force a full scan, which is slow. Use keywords of **three characters or more**. With multiple keywords, AND (match all) uses the index as long as at least one word has three or more characters, whereas OR (match any) skips the index if even one word has two characters or fewer.
- Filtering by custom fields can take longer than the other conditions. Try combining it with other conditions to narrow the target first.

### Known limitations

- `#CLEAR#` (clearing the assignee, due date, description, custom fields, or parent issue) is not documented in the official API specification, so it is **still being verified against a live space**.
- Writing free text entered as "Other" (otherValue) for a custom field is **not supported**. Multi-select custom fields whose option names contain a comma (or the Japanese comma `、`) cannot be imported either.
- Parent-child relationships support **two levels only (parent - child)**. Two new rows in the same file cannot be made parent and child.
- Keyword search is slow for words of two characters or fewer, because the index cannot be used.
- Keyword search covers only the issue key, summary, and description; comments and attachments are out of scope.
- The Bulk Update & Add template can be filtered by keyword, updated, created, status, and assignee (all issues if you specify nothing). Filtering by custom field is not supported.
- Some backend messages and all Excel output (headers and the `記入方法` sheet) are currently in Japanese only, even when the interface language is set to English.
